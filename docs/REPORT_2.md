### P1 - Issue 05's "compiles without churn" acceptance criterion is impossible in Go, and 218 call sites break

- Location: `docs/epics/epic-2-core-types-and-models-contracts/issues/05-provider-request-options.md:107-109` (the acceptance criterion), `:86-88` (the ripple estimate), `:156-163` (the PR size note built on both)
- Source: `docs/epics/epic-2-core-types-and-models-contracts/EPIC_2.md:26-27` (the `ProviderRequestOptions<TModel>` refactor) and `EPIC_2.md:55-56` (AC1, "the tree compiles"); `pipeline-interfaces.md` size rule ("L is approximately 500-1000. L is the ceiling, not the target")
- Problem: the criterion reads "Existing call sites still compile without churn: a caller writing `&ai.StreamOptions{APIKey: "k", Timeout: time.Second}` keeps working (embedded-field promotion), and a test asserts it." Go promotes embedded fields for **selectors** (`opts.APIKey` keeps working) but **not for composite-literal keys**. The moment `APIKey`/`Timeout`/`Headers`/`Env`/`MaxRetries`/`MaxRetryDelay`/`OnPayload`/`OnResponse` move into an embedded `ProviderRequestOptions` - which `:103-105` mandates - every keyed literal must become `&ai.StreamOptions{ProviderRequestOptions: ai.ProviderRequestOptions{...}}`. `grep -rn "StreamOptions{" --include=*.go .` filtered to those field names returns **218 lines** today (e.g. `ai/apis/anthropic/anthropic_oauth_test.go:39`, `ai/apis/anthropic/anthropic_error_mapping_test.go:51`). The claim at `:86-88` that "field promotion through an embedded struct usually means none" is therefore wrong.
- Impact: the acceptance criterion can never be ticked as written, so the implementer either abandons the embedding the epic asked for, or ticks a box that is false. Separately, 218 mandatory mechanical edits plus the struct split, `Fetch`, `SamplingParams`, two new option types, the `Model` field and two `docs/PORTING.md` entries put this PR straight through the ~1000-line ceiling the issue sets for itself at `:156-157`.
- Recommendation: rewrite `:107-109` to "field *access* is unchanged by promotion (`opts.APIKey` still compiles - a test asserts it); all keyed `StreamOptions` composite literals are mechanically rewritten to `ProviderRequestOptions: ai.ProviderRequestOptions{...}` - ~218 sites, mostly `_test.go`". Replace the estimate at `:86-88` with that count, and pre-split the issue: PR A = struct split + literal rewrite (mechanical, reviewable as a diffstat), PR B = `Fetch`, `SamplingParams`, `DeferredFetchOptions` / `DeferredCancelOptions`, `docs/PORTING.md`.

## Open questions

- Does `EPIC_2.md:26-27` require Go **embedding** specifically, or only that the transport knobs be reusable by the deferred option types? The 218-site literal churn in the P1 finding is a consequence of the mechanism issue 05 chose (`issues/05-provider-request-options.md:103-105`), not of the epic. A flat `StreamOptions` plus a separate `ProviderRequestOptions` used only by `DeferredFetchOptions` / `DeferredCancelOptions` would satisfy the epic at a fraction of the diff - and would itself be a `docs/PORTING.md` deviation worth recording.
- Is issue 06's `LazyStream` result-forwarding change a prerequisite for issue 10's `FetchDeferred` "runs through `LazyStream` ... and resolves to an `*AssistantMessage`" (`issues/10-deferred-response-dispatch.md:69-70`)? `ai/lazy.go` today ends the outer stream with `outer.End(nil)` and relies on the inner stream's terminal event having completed it. If an adapter's deferred fetch always emits a terminal `done` event this is fine and no dependency exists; if it can return without one, issue 10 needs `depends_on: 6`. Not flagged as a finding because it turns on adapter behaviour no issue in this epic implements.
