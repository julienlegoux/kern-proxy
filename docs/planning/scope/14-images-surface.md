# Question

In range: `src/images-models.ts` changed, `src/image-models.generated.ts` was
regenerated, `src/api/openrouter-images.ts` and
`src/providers/openrouter-images.ts` changed, and `scripts/generate-image-models.ts`
changed.

`SPECS.md` records `ai/images` as a **parallel public surface**: its own registry,
nothing in `ai` or `ai/providers` imports it, adapters self-register from
`init()`, and a consumer wanting image generation imports it directly. That
independence is the useful fact here — it means images can be sequenced freely.

But independence is not total: `ImagesOptions` now extends the new
`ProviderRequestOptions<ImagesModel<ImagesApi>>` (`types.ts`), so the core-type
migration in [decision 04](/scope/04-core-types-migration.md) does reach into it,
and the image catalog is regenerated by the same tooling as the model catalog
([decision 05](/scope/05-catalog-schema-and-tooling.md)).

# Options

- **In scope, its own small epic** — port the images changes and regenerate
  `data/images/openrouter.json` alongside the main catalog.
- **Types only** — make `ai/images` compile against the new
  `ProviderRequestOptions` and stop there; defer the adapter and catalog changes.
- **Out of scope entirely** — not available: the type change is forced, so
  `ai/images` must at minimum keep compiling.

# Recommendation

**In scope, but as the smallest unit — fold it into the catalog epic rather than
giving it its own.**

The forced part (compiling against `ProviderRequestOptions`) has to happen
regardless. The optional part is small and shares tooling with work already
scheduled: `generate-image-models.ts` and `image-models.generated.ts` are
regenerated by the same run that handles the model catalog, so splitting them
into a separate epic means touching `tools/export-catalog` twice.

Sequencing note for the epic: `ai/images` has exactly one live smoke test
(`ai/images/openrouter_test.go`, env-gated per `SPECS.md`), so CI will not catch
a regression in the OpenRouter images adapter. Whatever changes there deserves
an offline `httptest` case rather than relying on the gated smoke.

# Verdict

**In scope, folded into the catalog epic (milestone 2).** Accepted as
recommended.

The forced part — `ai/images` compiling against the new
`ProviderRequestOptions<ImagesModel<ImagesApi>>` — happens regardless. The
optional part is small and shares `tools/export-catalog` with work already
scheduled, so a separate epic would mean touching that tool twice.

Carried into the epic as an acceptance criterion: `ai/images` has exactly one
live smoke test (`ai/images/openrouter_test.go`, env-gated), so CI cannot catch
a regression in the OpenRouter images adapter. Any change there gets an offline
`httptest` case rather than relying on the gated smoke.
